## Rationale

This phase originated from validating the plugin's Freemius integration against Freemius's own documentation: is the "split builder" (a Vite compile-time flag producing separate free/premium JS bundles, [PHASE62_REPORT.md](archive/phases/PHASE62_REPORT.md) P62-F/G) really the right approach, and is the setup actually correct per Freemius's official instructions?

The split-builder approach is confirmed correct and Freemius-sanctioned. Freemius documents two supported paths for a freemium product: their own automatic file/folder preprocessor (`__premium_only` suffixes, `is__premium_only()` blocks, `@fs_premium_only`/`@fs_ignore` meta tags — [Software Licensing](https://freemius.com/help/documentation/wordpress-sdk/integration/software-licensing/), [Deployment Process](https://freemius.com/help/documentation/wordpress/deployment-process/)), or a self-managed fallback:

> "If you have already developed free and premium versions that are fundamentally different, you can either merge the versions into a single codebase or ignore the free version generated by Freemius. If you go with the 2nd option, make sure also to integrate the SDK into your free version and set the `is_premium` flag to false to indicate the SDK it is running in the scope of the free version." — [Software Licensing, "Managing One Codebase for Both Free and Premium Versions"](https://freemius.com/help/documentation/wordpress-sdk/integration/software-licensing/)

This repo (Phase 62, P62-F) chose the fallback for a sound, already-documented reason: Freemius's stripper works on file/folder/text markers and cannot reach inside a single compiled Vite/React bundle. PHP correctly needs no stripping either — server code is license *enforcement* (`Mullion_License` + `enforce_license_gates()`), not premium *feature* code, so there's nothing for Freemius's preprocessor to remove there regardless of which path is used.

But comparing the current PHP bootstrap (`mullion_fs()` in `mullion-gallery.php`) against the fallback path's own stated requirement above surfaced a real gap: **the SDK's `is_premium` flag never actually varies between the two shipped ZIPs.** Both the free and premium packages ship byte-identical PHP with `is_premium` hardcoded to `false` in every code path, so even once real Freemius credentials exist, the premium ZIP would incorrectly self-report as the free package to Freemius. This was flagged in Phase 62's P62-K `NOTE (M2)` comment but deferred wholesale to "once the Freemius dashboard product exists" — correct for values that genuinely need the dashboard (`premium_slug`, the real `id`/`public_key`), but not for `is_premium`, `has_premium_version`, and `is_org_compliant`, which are structural facts about *which artifact is running*, resolvable today without any Freemius account.

Separately, the release pipeline itself only ships the premium channel: `.github/workflows/release.yml` produces one ZIP (premium only), and `.github/workflows/svn-deploy.yml` has a hard-fail guard that refuses to run at all, pending free-channel wiring explicitly named — but not implemented — in Phase 62's P62-I track ("update `release.yml` to also emit a free ZIP..., point `svn-deploy.yml` at that free ZIP, and remove the P62-G guard"). That wiring is pure CI/YAML work with no dependency on a live Freemius account, even though the rest of P62-I (Plugin Check, artwork, WP.org submission) genuinely is.

1. **What triggered it.** A user request to validate this repo's Freemius setup against Freemius's official docs, comparing [Software Licensing](https://freemius.com/help/documentation/wordpress-sdk/integration/software-licensing/) and [Deployment Process](https://freemius.com/help/documentation/wordpress/deployment-process/) line-by-line against the current `mullion_fs()` bootstrap and release pipeline.
2. **Why it belongs together.** Both gaps are pure code/CI work that were bundled with genuinely-blocked human milestones (M1-M4) for expediency in Phase 62, not because they share a dependency on those milestones. They share one theme: making the already-designed split-build model self-consistent end-to-end (PHP identity, release artifacts, and the docs describing them), not just JS-code-complete.
3. **Success.** Building `wp-plugin/mullion-gallery/assets/` via `npm run build:wp` vs. `npm run build:wp:free` produces a package that correctly reports its own edition to Freemius with zero manual configuration; a single `Release` workflow run produces both a premium and a lite ZIP; `SVN Deploy` publishes the lite ZIP without a hard-coded guard; and `PACKAGING_RELEASE.md` stops being a stale trap for anyone packaging manually.

> **Relationship to Phase 62.** This phase does not re-plan or duplicate any of P62-A through P62-K. It picks up exactly two threads Phase 62 explicitly left as forward pointers (the `NOTE (M2)` in `mullion_fs()`, and P62-I's "absorbed from P62-G(g)" release-wiring sub-task) and implements the parts of each that don't require the Freemius account. Plugin Check, WP.org submission, store artwork, and pricing config remain out of scope, still blocked on M1, still owned by P62-I / the [Go-Live Punch List](guides/GO_LIVE_PUNCH_LIST.md).

## Sources (Freemius official documentation)

Every Freemius-behavior claim in this report was verified directly against Freemius's own docs, not inferred:

- **[Control Free and Premium WordPress Features with Freemius Licensing](https://freemius.com/help/documentation/wordpress-sdk/integration/software-licensing/)** — under "Managing One Codebase for Both Free and Premium Versions": the "ignore the free version generated by Freemius... set the `is_premium` flag to false" guidance quoted above — the direct source for the P75-A gap. Also the source for the `__premium_only` PHP method-suffix / file-suffix / `@fs_premium_only` / `@fs_ignore` / JS-CSS `/*! <fs_premium_only> */` comment-block syntax.
- **[Deployment Process](https://freemius.com/help/documentation/wordpress/deployment-process/)** — confirms: (a) *"Freemius prepares the WordPress.org-compatible package, but it does not publish it to WordPress.org for you"* — developers always own the actual SVN publish step, consistent with this repo's self-deploy model; (b) *"Ensure that your product has a 'Free' plan. If you haven't defined a 'Free' plan, only the premium version will be generated when you deploy your product"* — relevant context for M1 (Freemius product/plan setup), not this phase's scope; (c) the `__premium_only` file/folder suffix and `@fs_premium_only` meta-tag conventions (corroborates the first source).
- **[Integration with SDK](https://freemius.com/help/documentation/getting-started/integration-with-sdk/)** — source for the `vendor/freemius` SDK placement convention and the "don't hook the integration snippet on `plugins_loaded`" requirement, both already correctly followed by the current `mullion_fs()` bootstrap (no change needed there).

## Key Decisions

| # | Decision | Resolution |
|---|----------|------------|
| A | Marker mechanism: generated PHP class vs. a JSON marker file | **JSON marker** (`mullion-edition.json`), written by `scripts/copy-wp-assets.js` directly into `assets/`. No PHP codegen/escaping risk, and it naturally lives inside the directory `copy-wp-assets.js` already wipes-and-regenerates every build — nothing new to keep in sync. |
| B | Default `is_premium` when the marker is absent (e.g. local dev that never ran `copy-wp-assets.js`, or the PHPUnit CI job, which never runs a JS build at all) | **`true` (premium)** — mirrors `vite.config.ts`'s own `process.env.MULLION_PREMIUM !== 'false'` check, i.e. "premium is the default edition" is already this codebase's established convention; the marker only flips it to free when a free build explicitly ran. |
| C | `has_premium_version` / `is_org_compliant` vs. `premium_slug` / real `id`/`public_key` | The former two are **fixed values, set now** (`true`/`true`) — they're structural facts about this product's design (there's always a premium sibling; the split-build model was designed to be WP.org compliant), independent of M1. The latter three stay **filter-only, unfilled** — they genuinely cannot exist before the Freemius dashboard product does; inventing placeholders for them would be worse than leaving them blank. |
| D | Inline the `fs_dynamic_init()` args construction in `mullion_fs()` (as today) vs. extract it to a pure function | **Extract** to `mullion_freemius_init_args(array $config): array`. `mullion_fs()` itself is untestable without real credentials (it always returns `null` in CI/dev); pulling the args-merge logic into a pure, credential-free function makes it directly unit-testable, matching the existing no-op-safe testing pattern (`Mullion_License_Test`). |
| E | Where to run the free-build Pro-code leak gate for a release: a third full rebuild-and-check in `release.yml`, or a cheaper static re-scan? | **Three-layer, no redundant rebuild.** (1) `ci.yml`'s existing `npm run check:free-build` (full build + scan) keeps gating every PR — unchanged. (2) `release.yml` adds a **zero-extra-build static re-scan** (`node scripts/check-free-build-clean.mjs wp-plugin/mullion-gallery/assets`) of the lite assets it just built, right before zipping. (3) `svn-deploy.yml` adds the same static re-scan against the **independently downloaded-and-extracted** lite ZIP, right before the SVN push — the most valuable of the three, since it checks the literal bytes about to reach WP.org, decoupled from whatever produced them. |
| F | Lite ZIP naming convention | **`mullion-gallery-lite-v${VERSION}.zip`** — "lite" is the term already used consistently across `readme.txt`, `PRO_FEATURES.md`, and `MARKETPLACE_READINESS.md` for the free WP.org edition; reusing it avoids introducing a second name for the same thing. Slug itself stays singular (`mullion-gallery`) per Phase 74's Key Decision C — only the ZIP filename carries `-lite-`. |

## Track P75-A - Package edition self-identification

### Problem

`wp-plugin/mullion-gallery/mullion-gallery.php`'s `mullion_fs()` hardcodes `'is_premium' => false` in both the `mullion_freemius_config` filter's default bag and the `fs_dynamic_init()` args array. `includes/class-mullion-license.php::get_config()` duplicates the same hardcoded default (necessarily — `mullion_fs()` is defined *before* `Mullion_License` is `require_once`'d, so it can't delegate; already documented and refuted-as-a-defect in Phase 62's PR review, finding F3). Freemius's own SDK-bypass mechanism — [quoted above](https://freemius.com/help/documentation/wordpress-sdk/integration/software-licensing/) — depends on this flag correctly telling Freemius which of the two ZIPs is running, independent of `Mullion_License::can_use_premium_code()`, which is a separate, already-correct *entitlement* concept. Today, both the free and premium PHP payloads are byte-identical (by design — server code is license-enforcement, not premium feature code) and both would report `is_premium => false` regardless of which ZIP a site installed, once real credentials exist. `has_premium_version` and `is_org_compliant` are absent entirely from the `fs_dynamic_init()` args.

### Fix

**New: a build-emitted edition marker.**

- `scripts/copy-wp-assets.js` — after `copyRecursive(distDir, pluginAssetsDir)`, write `wp-plugin/mullion-gallery/assets/mullion-edition.json`:
  ```json
  { "premium": true, "generatedAt": "2026-07-27T00:00:00.000Z" }
  ```
  computed via `process.env.MULLION_PREMIUM !== 'false'` — the *exact same check* as `vite.config.ts`'s `define.__MULLION_PREMIUM__`, so the JS DCE flag and the PHP-reported package identity can never disagree. Written on every `npm run build:wp` and `npm run build:wp:free` run (both already invoke `copy-wp-assets.js`); like the rest of `assets/`, it's gitignored and gets overwritten (not merged) each build.

**Changed: `wp-plugin/mullion-gallery/mullion-gallery.php`.** Three new small functions, added before the existing `mullion_fs()` block, each individually `function_exists`-guarded (matching the file's existing defensive style):

- `mullion_edition_marker_path(): string` — `apply_filters('mullion_edition_marker_path', MULLION_PLUGIN_DIR . 'assets/mullion-edition.json')`. Filterable so tests can point it at a fixture without touching the real `assets/` directory.
- `mullion_is_premium_package(): bool` — reads the marker at that path; returns `true` if the file is missing, unreadable, or the JSON is malformed/missing the `premium` key (the "premium is the default edition" fallback — Key Decision B); otherwise returns `(bool) $data['premium']`.
- `mullion_freemius_init_args(array $config): array` — the pure merge helper that replaces the inline array literal currently passed to `fs_dynamic_init()`. Defaults now include `'is_premium' => mullion_is_premium_package()`, plus the two new fixed values `'has_premium_version' => true` and `'is_org_compliant' => true`; `$config` is still merged last, so the `mullion_freemius_config` filter remains the final override for every key, including these two.

`mullion_fs()` changes minimally: its own `$config` default bag's `'is_premium' => false` becomes `'is_premium' => mullion_is_premium_package()`, and the `fs_dynamic_init(array_merge([...], $config))` call becomes `fs_dynamic_init(mullion_freemius_init_args($config))`.

The `NOTE (M2)` comment is tightened to reflect that `is_premium`/`has_premium_version`/`is_org_compliant` are now resolved by this track; only `premium_slug` and the real `id`/`public_key` remain to reconcile at M2.

**Changed: `includes/class-mullion-license.php::get_config()`.** Same default-bag fix, guarded: `'is_premium' => function_exists('mullion_is_premium_package') ? mullion_is_premium_package() : true,` — the duplication is intentional and already documented as bootstrap-order-forced (P62 PR Review #2, finding F3); this track keeps both copies in sync rather than trying to remove the duplication (out of scope, would require reordering the plugin's `require_once` list).

### Acceptance criteria

- `npm run build:wp` produces `wp-plugin/mullion-gallery/assets/mullion-edition.json` with `"premium": true`; `npm run build:wp:free` produces the same file with `"premium": false`.
- With no marker file present (e.g. a fresh checkout, or the PHPUnit CI job, which never runs a JS build), `mullion_is_premium_package()` returns `true`.
- `mullion_freemius_init_args([])` returns an array with `has_premium_version === true` and `is_org_compliant === true` unconditionally, and `is_premium` following the marker.
- Passing an explicit `is_premium` (or any other key) in `$config` to `mullion_freemius_init_args()` always wins over the marker-derived default — the `mullion_freemius_config` filter remains the final override.
- `mullion_fs()` remains a safe no-op with zero network calls whenever `id`/`public_key` are empty — unchanged behavior, this track only changes what `is_premium` etc. *would* resolve to if credentials existed.

### Validation

- **New PHPUnit test file** `wp-plugin/mullion-gallery/tests/Mullion_Package_Edition_Test.php`:
  - `test_defaults_premium_without_marker_file` — asserts the marker path doesn't exist in the test environment and `mullion_is_premium_package()` returns `true`.
  - `test_reads_free_from_marker_file` / `test_reads_premium_from_marker_file` — via `add_filter('mullion_edition_marker_path', ...)` pointed at a `sys_get_temp_dir()` fixture, write `{"premium":false}` / `{"premium":true}`, assert the matching return value (proves it actually reads the file, not just always falling back); `tearDown()` deletes the fixture and removes the filter.
  - `test_malformed_marker_falls_back_to_premium` — fixture contains invalid JSON; asserts `true`.
  - `test_missing_premium_key_falls_back_to_premium` — fixture is valid JSON (`{}`) but has no `premium` key; asserts `true`.
  - `test_freemius_init_args_sets_fixed_freemium_flags` — calls `mullion_freemius_init_args([])` directly (no SDK, no credentials needed) and asserts `has_premium_version`, `is_org_compliant`, `slug`, and `menu['slug']`.
  - `test_freemius_init_args_config_overrides_marker` — calls `mullion_freemius_init_args(['is_premium' => false, 'id' => '123'])` with no marker present (which would otherwise default `true`); asserts the returned `is_premium === false` and `id === '123'`, proving `$config` always wins.
- **Updated** `Mullion_License_Test::test_get_config_defaults_empty_credentials` — the asserted `is_premium` default changes from `false` to `true` (no marker exists in the PHPUnit CI job), with an inline comment explaining this is the intended P75-A behavior change, not a regression.
- `php -l` on the two changed files (already CI-gated repo-wide in `test-php`).
- No new Vitest unit test for `copy-wp-assets.js`'s marker-writing logic — consistent with that script's existing untested-by-design status (it has zero unit tests today; correctness is proven by running it). Verified instead via the phase-wide Verification section below (local build dry-run, inspect the emitted JSON).

## Track P75-B - Dual-channel release pipeline

### Problem

`.github/workflows/release.yml` only ever runs `npm run build:wp` (premium) and produces a single ZIP. `.github/workflows/svn-deploy.yml` has a hard-fail guard (lines 32-42) that unconditionally errors: pushing the current release ZIP to WordPress.org would leak Pro code, so the workflow refuses to run at all. This was explicitly deferred to P62-I, whose own text names the exact fix ("update `release.yml` to also emit a free ZIP..., point `svn-deploy.yml` at that free ZIP, and remove the P62-G guard") — this track implements exactly that, without touching any of P62-I's genuinely M1-blocked parts (Plugin Check, artwork, WP.org submission).

### Fix

**`.github/workflows/release.yml`** — after the existing premium build+zip steps (renamed "Package **premium** distribution ZIP" for symmetry, otherwise unchanged), add:

1. **Build free (lite) assets** — `run: npm run build:wp:free`. This rebuilds JS with `MULLION_PREMIUM=false` and **overwrites** `wp-plugin/mullion-gallery/assets/` (per the split-build model — free and premium assets can't coexist there), including regenerating `mullion-edition.json` with `"premium": false` (P75-A). **Ordering constraint, called out explicitly in the step's comment:** this step must run *after* the premium ZIP is already created, since it destroys the premium assets on disk that the ZIP step already captured as bytes.
2. **Verify free (lite) assets are Pro-code clean** — `run: node scripts/check-free-build-clean.mjs wp-plugin/mullion-gallery/assets`. A static scan of the assets just built (see `check-free-build-clean.mjs` changes below) — zero extra build cost, since it doesn't rebuild, it inspects what step 1 already produced.
3. **Package lite distribution ZIP** — same `zip -x` exclude list as the premium step, output `mullion-gallery-lite-v${VERSION}.zip`, exposed as `steps.zip_lite.outputs.zip_path`.
4. **Create GitHub Release** — `files:` becomes a multi-line block listing both `steps.zip.outputs.zip_path` and `steps.zip_lite.outputs.zip_path`, so both ZIPs attach to the same release.
5. **Upload release ZIP artifact** — add a second `actions/upload-artifact@v4` step (`name: release-zip-lite`) for the lite ZIP, mirroring the existing premium one.

No changes to the premium build, Vitest sanity gate, or PHPUnit sanity gate steps — the PHP side is identical in both editions by design, so the already-run `composer install --no-dev` output is reused for both ZIPs without re-running.

**`scripts/check-free-build-clean.mjs`** — small, backward-compatible change: `const DIST_ASSETS = process.argv[2] || './dist/assets';`. `npm run check:free-build` (used by `ci.yml`) is unaffected — it calls the script with no arg, still defaults to `./dist/assets`. The new optional CLI arg lets `release.yml` and `svn-deploy.yml` re-scan an arbitrary already-built assets directory without rebuilding.

**`.github/workflows/svn-deploy.yml`** — remove the "Guard — free build required for WordPress.org (P62-G)" step entirely. Add `actions/setup-node@v4` (node 20; the check script has zero npm dependencies, so no `npm ci` is needed). Change the download/extract steps' `ZIP_NAME` from `mullion-gallery-v${VERSION}.zip` to `mullion-gallery-lite-v${VERSION}.zip` — the internal folder structure inside the ZIP is still `mullion-gallery/...` (only the outer filename gains `-lite-`), so `BUILD_DIR: deploy-dir/mullion-gallery` in the final SVN-deploy step is unchanged. Insert a new step immediately after extraction: **Verify downloaded build is Pro-code clean** — `run: node scripts/check-free-build-clean.mjs deploy-dir/mullion-gallery/assets` — before the "Deploy to WordPress.org SVN" step. Update the workflow's header comment to describe the new lite-ZIP flow instead of the removed guard.

### Acceptance criteria

- A `Release` workflow run produces exactly two ZIPs attached to the GitHub Release: `mullion-gallery-v${VERSION}.zip` (premium, byte-identical to today's output) and `mullion-gallery-lite-v${VERSION}.zip` (free, Pro code stripped, `mullion-edition.json` reports `premium: false`).
- `release.yml`'s new static re-scan step fails the workflow if the just-built lite assets contain any Pro chunk/marker (same violations `check-free-build-clean.mjs` already knows about — no new markers needed for this track).
- `svn-deploy.yml` runs to completion (no hard guard), downloads and deploys the **lite** ZIP, and its own re-scan step fails the deploy if the downloaded-and-extracted ZIP is not clean.
- `.distignore` (already the canonical exclude list per P62-K) needs no changes — both ZIPs use the same exclude set, since PHP doesn't differ between editions.

### Validation

- `php -l` unaffected (no PHP changes in this track).
- Local dry-run without triggering the real workflow (see phase-wide Verification below) — this is the primary way to prove the YAML logic before it ever runs in Actions, since `workflow_dispatch` can't be exercised locally.
- Manual review of the YAML diff for step-ordering correctness (the ordering constraint in the Fix section above is the one genuine footgun — a future reorder that runs the free build before the premium zip would silently ship a stripped-down "premium" ZIP).
- No `actionlint`/`yamllint` tooling exists in this repo today; out of scope to add it here — manual review plus the local dry-run substitute for automated YAML linting.

## Verification (phase-wide)

Proving both ZIPs come out correct end-to-end without running the real GitHub Actions workflow:
